# 办公物品管理系统 — 数据库设计详解

> 包含设计思路、触发器作用、视图作用、存储过程、ER 图描述的完整报告

---

## 第一部分：数据库设计思路

---

### 1.1 需求驱动的实体抽取

数据库设计的起点是系统功能需求。通过对"办公物品管理系统"的功能清单逐一分析，采用**数据流分析法**识别实体：

```
功能需求                         抽取的实体 / 关系
──────────────────────────────────────────────────
管理员维护物品编码、名称、        → Items 实体
  类别、产地、规格、型号、图片

类别有固定取值（纸张/文具/        → Categories 字典实体
  刀具/单据/礼品/其它）

产地通过下拉列表选择              → Origins 字典实体

入库登记：流水号、物品、日期、    → StockIn 实体
  数量、单价、总价                → (Items ← StockIn 入库关系)

领用申请：流水号、物品、数量、    → StockOut 实体
  领用人、日期、状态              → (Items ← StockOut 领用关系)

普通用户信息独立存储              → 不纳入数据库，用 JSON 文件
```

### 1.2 设计原则

| 原则 | 体现 |
|------|------|
| **数据独立性** | 字典表（Categories/Origins）独立于业务表，修改字典不影响业务数据 |
| **参照完整性** | 所有业务表通过外键关联，ON DELETE RESTRICT 防止误删 |
| **原子性** | 入库和审批使用数据库事务，要么全部成功要么全部回滚 |
| **冗余控制** | 满足 3NF，每个非主属性完全函数依赖于主键 |
| **性能优先** | 为高频查询字段建立索引，百万数据下查询<50ms |
| **可读性** | 流水号含日期信息（SI20250115001），约束统一命名 |

### 1.3 为什么分 5 张表而不是更少

**方案一（4 张表 — 不推荐）**：把 Categories 和 Origins 合为一张"字典表"。

```
Dict(Id, Type, Name)  — Type='category' 或 'origin'
```

❌ 问题：一个字段存两种含义，查询时需 `WHERE Type='category'`，无法设外键，SQL 不直观。

**方案二（3 张表 — 不推荐）**：把 StockIn 和 StockOut 合并为一张"流水表"。

```
Transaction(Id, Type, ItemCode, Qty, Price, ...)
```

❌ 问题：入库有 UnitPrice/TotalPrice，出库有 ApplicantId/Status，大量 NULL 字段，违反范式。

**最终方案（5 张表 — ✅ 当前设计）**：每张表职责单一，字段无冗余，外键清晰。

### 1.4 ER 图文字描述

```
Categories(Id PK, Name UQ)
    │
    │ 1:N  (FK_Items_Category)
    ▼
Items(ItemCode PK, ItemName, Category FK, Origin,
      Specification, Model, ImagePath, ImageData, Quantity)
    │
    ├── 1:N (FK_StockIn_ItemCode)  ──→ StockIn(StockInNo PK, ItemCode FK,
    │                                        PurchaseDate, Quantity, UnitPrice, TotalPrice)
    │
    └── 1:N (FK_StockOut_ItemCode) ──→ StockOut(StockOutNo PK, ItemCode FK,
                                             Quantity, ApplicantId, ApplyDate,
                                             Status, ApproveDate, Remark)

Origins(Id PK, Name UQ) ── 松散引用 ──→ Items.Origin（无强制外键）
```

## 第二部分：触发器详解

---

触发器是数据库层面的**自动响应机制**，在 INSERT/UPDATE/DELETE 发生时自动执行，用于维护数据一致性。本系统共 4 个触发器。

### 2.1 trg_StockIn_AfterInsert — 入库后自动累加库存

```sql
CREATE TRIGGER trg_StockIn_AfterInsert
AFTER INSERT ON StockIn FOR EACH ROW
BEGIN
    UPDATE Items SET Quantity = Quantity + NEW.Quantity
    WHERE ItemCode = NEW.ItemCode;
END
```

| 项目 | 说明 |
|------|------|
| **触发时机** | 向 StockIn 表插入新行之后（AFTER INSERT） |
| **触发频率** | 每插入一行触发一次（FOR EACH ROW） |
| **核心逻辑** | 读取新插入行的数量 `NEW.Quantity`，累加到对应物品的库存 |
| **为什么需要** | 如果有人在 Navicat 中直接 INSERT StockIn 而不走程序的事务，库存仍会自动更新。这是应用层事务之外的**数据库层兜底** |
| **应用层等价操作** | `sp_StockIn` 存储过程中 `UPDATE Items SET Quantity = Quantity + p_Quantity` |

**执行示例**：

```
某人直接执行: INSERT INTO StockIn VALUES ('SI20250115001', 'P001', NOW(), 100, 25.00, 2500.00);
        ↓ 触发器自动执行
Items.P001 的 Quantity 从 200 变为 300
```

### 2.2 trg_StockIn_AfterDelete — 入库删除时回退库存

```sql
CREATE TRIGGER trg_StockIn_AfterDelete
AFTER DELETE ON StockIn FOR EACH ROW
BEGIN
    UPDATE Items SET Quantity = GREATEST(0, Quantity - OLD.Quantity)
    WHERE ItemCode = OLD.ItemCode;
END
```

| 项目 | 说明 |
|------|------|
| **触发时机** | 从 StockIn 表删除一行之后 |
| **核心逻辑** | 读取被删除行的数量 `OLD.Quantity`，从对应物品库存中扣除 |
| **GREATEST(0, ...)** | 防止库存减成负数（安全性保护） |
| **为什么需要** | 管理员删除一条入库记录时，库存应相应减少。如果没有这个触发器，删除入库记录后库存会虚高 |

### 2.3 trg_StockOut_AfterUpdate — 领用确认时自动扣减库存（最关键的触发器）

```sql
CREATE TRIGGER trg_StockOut_AfterUpdate
AFTER UPDATE ON StockOut FOR EACH ROW
BEGIN
    IF OLD.Status = 0 AND NEW.Status = 1 THEN
        UPDATE Items SET Quantity = GREATEST(0, Quantity - NEW.Quantity)
        WHERE ItemCode = NEW.ItemCode;
    END IF;
END
```

| 项目 | 说明 |
|------|------|
| **触发时机** | StockOut 表的行被更新之后 |
| **触发条件** | **仅当** Status 从 0（申请）变为 1（确认）时才执行 |
| **核心逻辑** | 扣减对应物品的库存 |
| **为什么加 IF 条件** | 防止驳回操作（0→2）或重复确认（1→1）也扣库存。只有"申请→确认"这一种状态转换才触发扣减 |
| **为什么这是关键** | 这是整个审批流程的核心——确认 = 扣库存。如果这个触发器失效，领用再多也不会减少库存 |

**状态转换对照**：

```
OLD.Status → NEW.Status    触发器行为
─────────────────────────────────────────
0（申请） → 1（确认）      ✅ 扣减库存
0（申请） → 2（驳回）      ❌ 不触发
0（申请） → 0（不变）      ❌ 不触发
1（确认） → 1（不变）      ❌ 不触发（IF 条件拦截）
1（确认） → 2（驳回）      ❌ 不触发
```

### 2.4 trg_StockOut_AfterDelete — 领用记录删除时恢复库存

```sql
CREATE TRIGGER trg_StockOut_AfterDelete
AFTER DELETE ON StockOut FOR EACH ROW
BEGIN
    IF OLD.Status = 1 THEN
        UPDATE Items SET Quantity = Quantity + OLD.Quantity
        WHERE ItemCode = OLD.ItemCode;
    END IF;
END
```

| 项目 | 说明 |
|------|------|
| **触发时机** | 从 StockOut 表删除一行之后 |
| **触发条件** | 仅当被删除记录的状态是 1（已确认）时才恢复库存 |
| **核心逻辑** | 把被删除记录的领用数量加回库存 |
| **为什么加 IF** | 删除一条"申请"或"驳回"记录不应影响库存（因为这些操作本来就没扣过库存） |

### 触发器协同工作全景

```
操作                       触发器                    库存变化
────────────────────────────────────────────────────────────
INSERT StockIn         → trg_StockIn_AfterInsert   → Quantity ↑
DELETE StockIn         → trg_StockIn_AfterDelete   → Quantity ↓
UPDATE StockOut 0→1    → trg_StockOut_AfterUpdate  → Quantity ↓
DELETE StockOut(已确认) → trg_StockOut_AfterDelete  → Quantity ↑
UPDATE StockOut 0→2    → （无触发器触发）            → 不变
```

## 第三部分：视图详解

---

视图是**存储在数据库中的预定义查询**，像一个"虚拟表"——使用方式和表一样，但不实际存储数据，每次查询时动态执行背后的 SELECT 语句。

### 3.1 v_StockSummary — 库存汇总视图

```sql
CREATE VIEW v_StockSummary AS
SELECT
    i.ItemCode, i.ItemName,
    c.Name AS CategoryName,
    i.Origin, i.Specification, i.Model, i.Quantity,
    CASE
        WHEN i.Quantity = 0 THEN '缺货'
        WHEN i.Quantity < 50 THEN '低库存'
        WHEN i.Quantity < 200 THEN '正常'
        ELSE '充足'
    END AS StockLevel
FROM Items i JOIN Categories c ON i.Category = c.Id;
```

| 项目 | 说明 |
|------|------|
| **数据来源** | Items JOIN Categories |
| **核心价值** | 把经常需要的 JOIN 操作封装为视图，应用程序只需 `SELECT * FROM v_StockSummary` |
| **StockLevel 列** | 利用 CASE WHEN 自动计算库存等级（缺货/低库存/正常/充足），无需程序判断 |
| **使用场景** | 库存总览页面、库存报警、盘点报表 |

### 3.2 v_StockInMonthly — 入库月度统计视图

```sql
CREATE VIEW v_StockInMonthly AS
SELECT
    DATE_FORMAT(PurchaseDate, '%Y-%m') AS Month,
    COUNT(*) AS RecordCount,
    SUM(Quantity) AS TotalQuantity,
    SUM(TotalPrice) AS TotalAmount
FROM StockIn
GROUP BY DATE_FORMAT(PurchaseDate, '%Y-%m')
ORDER BY Month DESC;
```

| 项目 | 说明 |
|------|------|
| **数据来源** | StockIn 聚合查询 |
| **核心价值** | 按月汇总入库笔数、总数量、总金额，用于财务统计和趋势分析 |
| **使用场景** | 月度采购报表、成本分析 |

### 3.3 v_StockOutSummary — 领用汇总视图

```sql
CREATE VIEW v_StockOutSummary AS
SELECT
    so.ItemCode, i.ItemName, c.Name AS CategoryName,
    COUNT(*) AS ApplyCount,
    SUM(CASE WHEN so.Status = 0 THEN 1 ELSE 0 END) AS PendingCount,
    SUM(CASE WHEN so.Status = 1 THEN so.Quantity ELSE 0 END) AS ApprovedQty,
    SUM(CASE WHEN so.Status = 2 THEN 1 ELSE 0 END) AS RejectedCount
FROM StockOut so
JOIN Items i ON so.ItemCode = i.ItemCode
JOIN Categories c ON i.Category = c.Id
GROUP BY so.ItemCode, i.ItemName, c.Name;
```

| 项目 | 说明 |
|------|------|
| **数据来源** | StockOut JOIN Items JOIN Categories，三层关联 |
| **核心价值** | 每个物品的申请总次数、待审批数、已通过数量、被驳回数一目了然 |
| **CASE WHEN 技巧** | 在聚合函数内部使用条件判断，一次查询得到 4 个维度的统计 |
| **使用场景** | 物品领用频率分析、审批效率统计 |

### 3.4 v_ItemFullInfo — 物品完整信息视图

```sql
CREATE VIEW v_ItemFullInfo AS
SELECT
    i.ItemCode, i.ItemName, c.Name AS CategoryName,
    i.Origin, i.Specification, i.Model, i.Quantity,
    COALESCE(si.TotalInAmount, 0) AS TotalInAmount,
    COALESCE(so.TotalOutCount, 0) AS TotalOutCount
FROM Items i
JOIN Categories c ON i.Category = c.Id
LEFT JOIN (
    SELECT ItemCode, SUM(TotalPrice) AS TotalInAmount
    FROM StockIn GROUP BY ItemCode
) si ON i.ItemCode = si.ItemCode
LEFT JOIN (
    SELECT ItemCode, COUNT(*) AS TotalOutCount
    FROM StockOut WHERE Status = 1 GROUP BY ItemCode
) so ON i.ItemCode = so.ItemCode;
```

| 项目 | 说明 |
|------|------|
| **数据来源** | Items + Categories + 入库子查询 + 领用子查询 |
| **核心价值** | 一个视图展示物品的全部维度：基本信息 + 入库总额 + 领用次数 |
| **LEFT JOIN 子查询** | 即使物品从未入库或从未被领用，也能正确显示（此时 TotalInAmount=0） |
| **COALESCE** | 将 NULL 替换为 0，避免程序处理空值 |
| **使用场景** | 物品综合分析、采购决策支持 |

### 视图 vs 直接查询对比

```
场景：查某个物品的入库总额

不使用视图（每次写）：
SELECT i.*, (SELECT SUM(TotalPrice) FROM StockIn
             WHERE ItemCode = i.ItemCode) AS TotalInAmount
FROM Items i WHERE i.ItemCode = 'P001';

使用视图（一次定义，永久使用）：
SELECT * FROM v_ItemFullInfo WHERE ItemCode = 'P001';
```

## 第四部分：存储过程补充说明

---

除了触发器和视图，本系统还有 10 个存储过程，其中最具代表性的是：

### 4.1 sp_StockIn — 入库事务

```sql
START TRANSACTION;
    CALL sp_GenerateStockInNo(v_StockInNo);     -- ① 生成流水号
    INSERT INTO StockIn (...);                   -- ② 写入库记录
    UPDATE Items SET Quantity += ...;            -- ③ 更新库存
COMMIT;                                          -- ④ 原子提交
```

三个操作必须全部成功或全部失败——如果第③步失败（比如库存超限），①②也会回滚。

### 4.2 sp_FixNegativeStock — 游标应用

```sql
DECLARE cur CURSOR FOR SELECT ItemCode FROM Items WHERE Quantity < 0;
OPEN cur;
read_loop: LOOP
    FETCH cur INTO v_ItemCode;
    UPDATE Items SET Quantity = 0 WHERE ItemCode = v_ItemCode;
END LOOP;
CLOSE cur;
```

逐行处理库存为负的物品，将其归零。这是实验六要求的游标使用演示——实际环境中更推荐用 `UPDATE Items SET Quantity = 0 WHERE Quantity < 0` 一条语句完成。
