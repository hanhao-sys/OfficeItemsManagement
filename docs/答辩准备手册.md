### 1. 需求分析

#### 1.1 业务背景

某单位办公物品管理混乱，采购、领用全凭纸质登记。需要一套信息化系统实现：
- 物品库存实时可查
- 入库有据可查
- 领用需审批、可追溯
- 管理员与普通用户权限分离

#### 2.2 核心表结构

**Items（物品信息）**

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| ItemCode | VARCHAR(20) | PK | 物品编码 |
| ItemName | VARCHAR(100) | NOT NULL | 物品名称 |
| Category | INT | FK→Categories | 类别 |
| Origin | VARCHAR(100) | — | 产地 |
| Specification | VARCHAR(100) | — | 规格 |
| Model | VARCHAR(100) | — | 型号 |
| ImagePath | VARCHAR(500) | — | 图片路径 |
| Quantity | INT | DEFAULT 0, CHECK(≥0) | 库存数量 |

**StockIn（入库记录）**

| 字段 | 类型 | 说明 |
|------|------|------|
| StockInNo | VARCHAR(20) PK | 流水号：SI+日期+序号 |
| ItemCode | VARCHAR(20) FK | 物品编码 |
| PurchaseDate | DATETIME | 购买日期 |
| Quantity | INT CHECK(>0) | 入库数量 |
| UnitPrice | DECIMAL(18,2) | 单价 |
| TotalPrice | DECIMAL(18,2) | 总价=数量×单价 |

**StockOut（领用记录）**

| 字段 | 类型 | 说明 |
|------|------|------|
| StockOutNo | VARCHAR(20) PK | 流水号：SO+日期+序号 |
| ItemCode | VARCHAR(20) FK | 物品编码 |
| Quantity | INT CHECK(>0) | 领用数量 |
| ApplicantId | VARCHAR(50) | 领用人 ID |
| ApplyDate | DATETIME | 申请日期 |
| Status | INT DEFAULT 0 | 0=申请 1=确认 2=驳回 |

#### 2.3 完整性约束命名规则

```
PK_表名         主键约束
FK_表名_字段    外键约束
CK_表名_字段    CHECK 约束
UQ_表名_字段    UNIQUE 约束
IX_表名_字段    索引
```

#### 2.4 触发器设计

| 触发器 | 时机 | 作用 |
|--------|------|------|
| trg_StockIn_AfterInsert | INSERT 后 | `Items.Quantity += NEW.Quantity` |
| trg_StockIn_AfterDelete | DELETE 后 | `Items.Quantity -= OLD.Quantity` |
| trg_StockOut_AfterUpdate | UPDATE 后 | Status 0→1 时 `Items.Quantity -= NEW.Quantity` |
| trg_StockOut_AfterDelete | DELETE 后 | 已确认记录删除时恢复库存 |

#### 2.5 存储过程设计

| 存储过程 | 功能 | 技术点 |
|----------|------|--------|
| sp_GenerateStockInNo | 生成入库流水号 | CONCAT + LPAD |
| sp_StockIn | 事务入库 | START TRANSACTION → INSERT + UPDATE → COMMIT |
| sp_ApproveStockOut | 确认领用 | 状态校验 + 库存检查 + 事务扣减 |
| sp_RejectStockOut | 驳回领用 | 状态校验 |
| sp_StockInDetail | 分页查询入库明细 | LIMIT + OFFSET |
| sp_FixNegativeStock | 游标修正负库存 | CURSOR + LOOP |
| sp_TopCategoryByStockIn | 入库类别排行 | GROUP BY + JOIN + LIMIT |

#### 3.2 技术选型理由

| 技术 | 选型理由 |
|------|----------|
| **WPF (.NET 8)** | 桌面端首选，XAML 数据绑定强大，MVVM 模式成熟 |

## 第二部分：设计思想和开发过程讲解

---

### 讲解提纲（5-8分钟）

#### 开头（30秒）
> "我设计的是一套办公物品管理系统，解决单位办公用品采购入库、领用审批、库存查询的信息化需求。系统分为管理员桌面端和普通用户 Web 端，数据库使用 MySQL 8.4.8。"

#### 1. 需求分析（1分钟）
- 两种角色：管理员 vs 普通用户
- 管理员：用户维护、物品管理、入库登记、领用审批、库存查询
- 普通用户：查看库存、提交领用申请
- 核心约束：用户信息存文件，业务数据存数据库

#### 2. 数据库设计（1.5分钟）
- 5 张核心表：Items / StockIn / StockOut / Categories / Origins
- 外键关系：Items 双向关联入库和出库
- 触发器：自动维护库存一致性（入库累加、确认扣减）
- 存储过程：流水号生成、事务入库、分页查询、游标修正
- 完整性约束：PK_/FK_/CK_/UQ_ 前缀命名规范

#### 3. 系统架构（1分钟）
- 四层架构：表示层 → 业务逻辑层 → 数据访问层 → 数据存储层
- 管理端 WPF：Frame 导航 + 6 个 Page + MVVM
- Web 端 Razor Pages：3 个 PageModel + Session 认证
- 共用 Common 类库和 Data 数据层

#### 4. 关键技术点（1.5分钟）
- **入库事务**：`BEGIN TRANSACTION → INSERT StockIn → UPDATE Items.Quantity → COMMIT`，保证原子性
- **审批流程**：状态机 0→1 或 0→2，确认时事务扣库存，驳回不扣
- **100万条优化**：分页（LIMIT+OFFSET）、索引（IX_StockIn_ItemCode）、仅加载最近50条
- **异常处理**：WPF 中 `async void` 转 `Dispatcher.InvokeAsync` + 全局 `DispatcherUnhandledException` 兜底
- **JSON 用户存储**：Serializer/Deserializer + Unicode 不转义

#### 结尾（30秒）
> "此外还实现了实验六要求的 100 万条性能测试、4 个触发器、10 个存储过程、游标、视图和 GRANT 授权，数据库命令规范使用了完整性命名子句。"

## 第四部分：教师常见提问及回答

---

### 数据库相关

**Q1: 为什么要用触发器而不是只在代码里更新库存？**

A: 双层保障。代码层面（EF Core 事务）是第一道防线；触发器是数据库层面的最后防线——即使有人直接操作数据库 INSERT StockIn，库存也能自动更新。同时这也是实验六"集成触发器"的要求。

**Q2: 入库流水号为什么要用存储过程生成而不是自增 ID？**

A: 业务需要可读的流水号格式 `SI20250115001`（一眼能看出日期和序号）。自增 INT 主键无法满足这个格式要求。存储过程中用 `COUNT + CONCAT + LPAD` 生成，同时在 Repository 层用 `BeginTransaction` 保证并发安全。

**Q3: 100 万条记录下如何保证查询性能？**

A: 三个方面：(1) 索引 — `IX_StockIn_ItemCode`、`IX_StockIn_PurchaseDate`；(2) 分页 — `Skip/Take`（LIMIT/OFFSET）每页只取 20 条；(3) 限制加载量 — 入库页面只取最近 50 条，不做全表加载。用 EXPLAIN 验证执行计划，确认走索引。

**Q4: 为什么用户信息存在 JSON 文件而不是数据库？**

A: 这是实验明确要求"用户信息存在文件中（XML 或 JSON）"。JSON 相比 XML 更轻量，C# 的 `System.Text.Json` 序列化性能好，且可读性强。对于普通用户这种非高频读写的数据，文件存储完全够用。

**Q5: 外键约束的 ON DELETE RESTRICT 是什么含义？**

A: 限制删除——如果一个物品已经被入库或领用引用，不允许直接删除该物品，必须先删除关联的入库/出库记录。这保证了数据的引用完整性。

### 架构相关

**Q6: 为什么管理端用 WPF 而不用 Web？**

A: 实验要求"管理员采用桌面应用程序开发"，WPF 是 .NET 桌面开发的标准框架。桌面端相比 Web 端对本地文件操作（图片上传/复制）、Windows 原生控件（DatePicker/OpenFileDialog）支持更好。

**Q7: 为什么 Web 端选择 Razor Pages 而不是 MVC？**

A: Razor Pages 更简洁——每个页面一个 PageModel + 一个 cshtml，适合页面数量不多的中小项目。MVC 的 Controller/View 分离更适合大型项目。对于本系统 3 个页面，Razor Pages 代码更集中、更易理解。

**Q8: Common 和 Data 为什么要分成两个类库？**

A: 分层解耦。Common 是纯数据结构（POCO），不依赖 EF Core；Data 依赖 EF Core 和 Common。如果将来换成 Dapper 或 ADO.NET，只需要改 Data 层，Common 不用动。

**Q9: WPF 端为什么没用正式的依赖注入？**

A: WPF 的生命周期和 ASP.NET Core 不同——没有内置的 DI 容器和请求管道。可以使用 `Microsoft.Extensions.DependencyInjection` 手动构建，但为了代码简洁，这里用了 ServiceLocator 模式。在 Program.cs 中可以用 `HostBuilder` 方式引入 DI，这是可以改进的方向。

### 代码相关

**Q10: async void 在 WPF 中有什么问题？你怎么解决的？**

A: `async void` 的异常无法被 `try/catch` 捕获，会直接导致进程崩溃。解决方法是：事件处理器用同步方法 + `_ = Task` 启动异步任务，任务内部用 `try/catch` 包裹，同时注册 `DispatcherUnhandledException` 全局兜底。

**Q11: StockOut 页面 RadioButton 为什么会 NullReference？**

A: WPF 的 XAML 解析是顺序的。`RadioButton` 设置 `IsChecked="True"` 时立即触发 `Checked` 事件，但此时后面定义的 `DataGrid` 还未创建。解决方案：在 `ApplyFilter()` 开头加 `if (DgStockOut == null) return;`。

**Q12: DbContext 的生命周期你是怎么管理的？**

A: Web 端使用 `AddDbContext` 注册为 Scoped（每个请求一个实例），这是最佳实践。WPF 端用了单例（简化实现），生产环境建议 `IDbContextFactory<T>` 每次操作创建新实例。

### 加分项相关

**Q13: 游标在什么场景下使用？**

A: 在存储过程 `sp_FixNegativeStock` 中。游标逐行遍历库存为负的物品，逐个修正为零。这是实验要求的游标使用演示。实际开发中能用 SET 批量操作就不用游标（性能差）。

**Q14: 视图有什么实际作用？**

A: `v_StockSummary` 封装了 JOIN + CASE WHEN，将复杂的库存查询变成一个简单的 `SELECT * FROM v_StockSummary`。对应用程序透明——EF Core 可以像查表一样查视图。

**Q15: 完整性命名子句的意义？**

A: 给每个约束命名而不是让系统自动生成。好处：(1) 报错时能看出是哪个约束违反；(2) ALTER/DROP 时能精确操作；(3) 数据库文档自描述。
