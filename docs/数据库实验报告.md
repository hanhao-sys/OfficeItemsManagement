# 数据库实验报告

## 办公物品管理系统 — 数据库设计与实现

---

## 一、系统概述及需求分析

### 1.1 项目背景

某单位办公物品管理依赖纸质登记，存在以下问题：库存不透明、领用无追溯、入库缺记录。需要一套信息化系统实现办公物品的全生命周期管理。

### 1.2 系统目标

- 实现物品信息的数字化管理（编码、名称、类别、产地、规格、型号、图片）
- 实现入库登记，自动生成流水号、自动更新库存
- 实现领用申请与审批流程，确认后自动扣减库存
- 实现库存实时查询，支持多维度筛选和分页
- 管理员与普通用户权限分离

### 1.3 功能需求分析

| 角色 | 功能 | 数据操作 |
|------|------|----------|
| 管理员 | 物品信息维护 | Items CRUD |
| 管理员 | 入库登记 | StockIn INSERT → Items UPDATE |
| 管理员 | 领用审批 | StockOut UPDATE → Items UPDATE |
| 管理员 | 库存查询 | Items + Categories JOIN |
| 普通用户 | 库存查看 | Items + Categories JOIN |
| 普通用户 | 领用申请 | StockOut INSERT |
| 管理员 | 用户维护 | Users.json 文件 CRUD |

### 1.4 数据需求分析

**核心实体**：
- 物品（Item）：编码、名称、类别、产地、规格、型号、图片、库存数量
- 入库记录（StockIn）：流水号、物品编码、购买日期、数量、单价、总价
- 领用记录（StockOut）：流水号、物品编码、数量、领用人、日期、状态

**实体间关系**：
- 一个物品 → 多条入库记录（1:N）
- 一个物品 → 多条领用记录（1:N）
- 入库/领用记录必须关联已有物品（参照完整性）

**数据量预估**：
- 物品：数百条
- 入库记录：每年数千条（性能测试目标 100 万条）
- 领用记录：每年数百条

## 三、逻辑结构设计

### 3.1 关系模式

**Categories（类别字典）** — 关系模式：`Categories(Id, Name)`

| 属性 | 类型 | 约束 | 说明 |
|------|------|------|------|
| Id | INT | PRIMARY KEY, AUTO_INCREMENT | 类别编号 |
| Name | VARCHAR(50) | NOT NULL, UNIQUE | 类别名称 |

**Origins（产地字典）** — 关系模式：`Origins(Id, Name)`

| 属性 | 类型 | 约束 | 说明 |
|------|------|------|------|
| Id | INT | PRIMARY KEY, AUTO_INCREMENT | 产地编号 |
| Name | VARCHAR(100) | NOT NULL, UNIQUE | 产地名称 |

**Items（物品信息）** — 关系模式：`Items(ItemCode, ItemName, Category, Origin, Specification, Model, ImagePath, ImageData, Quantity)`

| 属性 | 类型 | 约束 | 说明 |
|------|------|------|------|
| ItemCode | VARCHAR(20) | PRIMARY KEY | 物品编码 |
| ItemName | VARCHAR(100) | NOT NULL | 物品名称 |
| Category | INT | FOREIGN KEY → Categories(Id) | 物品类别 |
| Origin | VARCHAR(100) | DEFAULT '' | 产地 |
| Specification | VARCHAR(100) | DEFAULT '' | 规格 |
| Model | VARCHAR(100) | DEFAULT '' | 型号 |
| ImagePath | VARCHAR(500) | DEFAULT '' | 图片文件路径（兼容） |
| ImageData | LONGBLOB | NULL | 图片二进制数据 |
| Quantity | INT | DEFAULT 0, CHECK(Quantity >= 0) | 库存数量 |

**StockIn（入库记录）** — 关系模式：`StockIn(StockInNo, ItemCode, PurchaseDate, Quantity, UnitPrice, TotalPrice)`

| 属性 | 类型 | 约束 | 说明 |
|------|------|------|------|
| StockInNo | VARCHAR(20) | PRIMARY KEY | 流水号 SI+日期+序号 |
| ItemCode | VARCHAR(20) | FOREIGN KEY → Items(ItemCode) | 物品编码 |
| PurchaseDate | DATETIME | NOT NULL | 购买日期 |
| Quantity | INT | CHECK(Quantity > 0) | 入库数量 |
| UnitPrice | DECIMAL(18,2) | CHECK(UnitPrice >= 0) | 单价 |
| TotalPrice | DECIMAL(18,2) | CHECK(TotalPrice >= 0) | 总价 |

**StockOut（领用/出库记录）** — 关系模式：`StockOut(StockOutNo, ItemCode, Quantity, ApplicantId, ApplyDate, Status, ApproveDate, Remark)`

| 属性 | 类型 | 约束 | 说明 |
|------|------|------|------|
| StockOutNo | VARCHAR(20) | PRIMARY KEY | 流水号 SO+日期+序号 |
| ItemCode | VARCHAR(20) | FOREIGN KEY → Items(ItemCode) | 物品编码 |
| Quantity | INT | CHECK(Quantity > 0) | 领用数量 |
| ApplicantId | VARCHAR(50) | NOT NULL | 领用人ID |
| ApplyDate | DATETIME | NOT NULL | 申请日期 |
| Status | INT | DEFAULT 0, CHECK(Status IN (0,1,2)) | 0=申请 1=确认 2=驳回 |
| ApproveDate | DATETIME | NULL | 审批日期 |
| Remark | VARCHAR(500) | NULL | 审批备注 |

### 3.2 完整性约束设计

所有约束采用**命名子句**规范，前缀含义如下：

| 前缀 | 含义 | 示例 |
|------|------|------|
| PK_ | PRIMARY KEY | PK_Items |
| FK_ | FOREIGN KEY | FK_StockIn_ItemCode |
| CK_ | CHECK | CK_Items_Quantity |
| UQ_ | UNIQUE | UQ_Categories_Name |

```
PK_Items          PRIMARY KEY (ItemCode)
PK_StockIn        PRIMARY KEY (StockInNo)
PK_StockOut       PRIMARY KEY (StockOutNo)

FK_Items_Category FOREIGN KEY (Category) REFERENCES Categories(Id)
FK_StockIn_Item   FOREIGN KEY (ItemCode) REFERENCES Items(ItemCode)
FK_StockOut_Item  FOREIGN KEY (ItemCode) REFERENCES Items(ItemCode)

CK_Items_Quantity CHECK (Quantity >= 0)
CK_StockIn_Qty    CHECK (Quantity > 0)
CK_StockIn_Price  CHECK (UnitPrice >= 0)
CK_StockIn_Total  CHECK (TotalPrice >= 0)
CK_StockOut_Qty   CHECK (Quantity > 0)
CK_StockOut_Status CHECK (Status IN (0, 1, 2))
```

### 3.3 数据完整性保证

| 类型 | 实现方式 |
|------|----------|
| **实体完整性** | 所有表设 PRIMARY KEY |
| **参照完整性** | FOREIGN KEY + ON DELETE RESTRICT（有关联记录不允许删物品） |
| **用户定义完整性** | CHECK 约束 + DEFAULT 值 |
| **触发器保证** | 入库自动加库存、确认自动减库存、删除自动回退 |

| 索引名 | 表 | 字段 | 类型 | 用途 |
|--------|------|------|------|------|
| IX_StockIn_ItemCode | StockIn | ItemCode | 普通索引 | 按物品查入库 |
| IX_StockIn_PurchaseDate | StockIn | PurchaseDate | 普通索引 | 按日期查入库 |
| IX_StockOut_ItemCode | StockOut | ItemCode | 普通索引 | 按物品查出库 |
| IX_StockOut_ApplicantId | StockOut | ApplicantId | 普通索引 | 按用户查领用 |
| IX_StockOut_Status | StockOut | Status | 普通索引 | 按状态筛选 |
| IX_Items_Category | Items | Category | 普通索引 | 按类别查物品 |
| IX_Items_ItemName | Items | ItemName | 普通索引 | 按名称搜索 |

**索引选择原则**：WHERE 条件高频列、JOIN 关联列、排序列

**百万条优化建议**（已记录在 `08_PerformanceTest.sql`）：
- 复合索引 `(ItemCode, PurchaseDate)` — 同时按物品和日期查询
- 覆盖索引 `(ItemCode, PurchaseDate, TotalPrice)` — 避免回表

### 4.4 性能测试结果

| 测试查询 | 百万条下预期 | 优化手段 |
|----------|:--------:|----------|
| `SELECT COUNT(*) FROM StockIn` | 2-5 秒 | 全表扫描，难以优化 |
| `WHERE ItemCode = 'P001' LIMIT 100` | < 50ms | IX_StockIn_ItemCode 索引 |
| `WHERE PurchaseDate BETWEEN` | < 100ms | IX_StockIn_PurchaseDate |
| `GROUP BY ItemCode` | 1-3 秒 | 聚合操作，需全表 |
| `JOIN Items` | 100-500ms | 两表索引配合 |

### 5.2 建表 SQL（核心代码）

```sql
CREATE TABLE Items (
    ItemCode      VARCHAR(20)   NOT NULL,
    ItemName      VARCHAR(100)  NOT NULL,
    Category      INT           NOT NULL,
    Origin        VARCHAR(100)  DEFAULT '',
    Specification VARCHAR(100)  DEFAULT '',
    Model         VARCHAR(100)  DEFAULT '',
    ImagePath     VARCHAR(500)  DEFAULT '',
    ImageData     LONGBLOB      NULL,
    Quantity      INT           DEFAULT 0,
    CONSTRAINT PK_Items PRIMARY KEY (ItemCode),
    CONSTRAINT FK_Items_Category FOREIGN KEY (Category)
        REFERENCES Categories(Id) ON DELETE RESTRICT,
    CONSTRAINT CK_Items_Quantity CHECK (Quantity >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 5.3 存储过程（核心代码）

**生成入库流水号**：

```sql
CREATE PROCEDURE sp_GenerateStockInNo(OUT outNo VARCHAR(20))
BEGIN
    DECLARE prefix VARCHAR(10);
    DECLARE seq INT;
    SET prefix = CONCAT('SI', DATE_FORMAT(NOW(), '%Y%m%d'));
    SELECT COUNT(*) + 1 INTO seq FROM StockIn
    WHERE StockInNo LIKE CONCAT(prefix, '%');
    SET outNo = CONCAT(prefix, LPAD(seq, 3, '0'));
END
```

**入库事务**：

```sql
CREATE PROCEDURE sp_StockIn(
    IN p_ItemCode VARCHAR(20), IN p_PurchaseDate DATETIME,
    IN p_Quantity INT, IN p_UnitPrice DECIMAL(18,2))
BEGIN
    DECLARE v_StockInNo VARCHAR(20);
    START TRANSACTION;
        CALL sp_GenerateStockInNo(v_StockInNo);
        INSERT INTO StockIn VALUES (v_StockInNo, p_ItemCode,
            p_PurchaseDate, p_Quantity, p_UnitPrice, p_Quantity * p_UnitPrice);
        UPDATE Items SET Quantity = Quantity + p_Quantity
        WHERE ItemCode = p_ItemCode;
    COMMIT;
END
```

**确认领用（事务）**：

```sql
CREATE PROCEDURE sp_ApproveStockOut(
    IN p_StockOutNo VARCHAR(20), IN p_Remark VARCHAR(500))
BEGIN
    DECLARE v_ItemCode VARCHAR(20);
    DECLARE v_Quantity INT;
    SELECT ItemCode, Quantity INTO v_ItemCode, v_Quantity
    FROM StockOut WHERE StockOutNo = p_StockOutNo;

    START TRANSACTION;
        UPDATE StockOut SET Status = 1, ApproveDate = NOW()
        WHERE StockOutNo = p_StockOutNo;
        UPDATE Items SET Quantity = Quantity - v_Quantity
        WHERE ItemCode = v_ItemCode;
    COMMIT;
END
```

### 5.6 游标

```sql
-- 批量修正负库存（游标演示）
CREATE PROCEDURE sp_FixNegativeStock()
BEGIN
    DECLARE done INT DEFAULT 0;
    DECLARE v_ItemCode VARCHAR(20);
    DECLARE cur CURSOR FOR
        SELECT ItemCode FROM Items WHERE Quantity < 0;
    DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = 1;

    OPEN cur;
    read_loop: LOOP
        FETCH cur INTO v_ItemCode;
        IF done THEN LEAVE read_loop; END IF;
        UPDATE Items SET Quantity = 0 WHERE ItemCode = v_ItemCode;
    END LOOP;
    CLOSE cur;
END
```

### 7.2 关键技术点

1. **完整性约束命名子句**：所有约束使用 PK_/FK_/CK_/UQ_ 前缀命名，符合数据库工程规范，便于维护和调试。

2. **触发器自动维护库存**：入库 → 自动累加库存，确认领用 → 自动扣减库存，删除记录 → 自动回退。在数据库层面保证数据一致性。

3. **存储过程实现事务**：入库和审批使用 `START TRANSACTION → DML → COMMIT`，保证多表操作的原子性。

4. **分页查询优化**：`LIMIT pageSize OFFSET (pageNo-1)*pageSize`，配合索引，百万级数据也能快速响应。

5. **应用程序双层保障**：EF Core 代码层面用 `BeginTransactionAsync()`，数据库层面用触发器，双重保证库存数据不会出错。

6. **游标演示**：在 `sp_FixNegativeStock` 中使用 CURSOR + LOOP 逐行处理异常数据，满足实验教学要求。

### 7.3 设计反思

**优点**：
- 约束命名规范，数据库自文档化
- 触发器 + 存储过程 + 应用事务，三层数据保护
- 索引设计针对实际查询场景，百万条数据可正常运行

**可改进方向**：
- 可引入分区表（按年份分区 StockIn），进一步提升大表查询性能
- 可增加审计日志表，记录所有数据变更操作
- 可将触发器逻辑迁移到应用层，减少数据库耦合
